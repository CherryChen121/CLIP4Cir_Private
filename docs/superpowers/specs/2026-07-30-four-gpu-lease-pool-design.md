# Combined GPU 队列四卡租约池与容错设计

## 背景

现有 Combined GPU 队列会在 GPU 连续空闲 5 分钟并通过最终复查后启动任务，但每个任务结束后会重新从全局候选卡中分配。现有队列还会在单个训练任务非零退出后暂停所有新派发。

本次修改把调度方式升级为最多 4 个持久 GPU 租约槽位：GPU 首次获取仍采用保守的 5 分钟审查；一旦获取，后续任务优先在同一张卡上运行，任务之间冷却 60 秒。单个训练任务失败只记录结果，不阻塞其他任务或 Phase B。

本轮只修改、测试、提交并本地合并代码，不启动 GPU 队列。真实运行等待用户后续明确命令。

## 目标

- 调度器同时持有的 GPU 租约最多为 4 个。
- 首次获取 GPU 时继续保护服务器上的已有任务。
- 已租用 GPU 在任务间优先复用，减少重复等待 5 分钟和频繁换卡。
- 冷却期间若其他用户开始使用该卡，立即放弃租约，不与其争用下一任务。
- 单个任务失败、中断或启动失败不阻塞队列中的其他任务。
- Phase A 的全部任务处理完后，无论其中是否有失败，都继续进入 Phase B。
- 日志和状态能够完整解释租约获取、冷却、复用、释放及任务失败。

## 不在本次范围

- 不自动重试失败任务。
- 不自动修改训练超参数、模型命令或数据集。
- 不修改用户当前未提交的 `命令.sh`。
- 不启动 Phase C。
- 不提供操作系统级 GPU 独占。
- 不终止其他用户进程。
- 不在实现完成后自动启动 systemd 服务。

## 方案选择

采用“调度器内置四槽位持久租约池”。

不采用只限制运行任务数的无状态方案，因为任务结束后仍会重新选卡，无法满足固定使用原卡的目标。不采用每张 GPU 一个常驻 Worker 的方案，因为会大幅重构当前调度器、状态恢复和 Phase 屏障，收益不足。

## GPU 租约模型

状态文件增加顶层 `leases`，每个租约至少记录：

- `gpu_index`
- `gpu_uuid`
- `state`：`running` 或 `cooldown`
- `task_id`
- `previous_task_id`
- `cooldown_ready_at`
- `acquired_at`
- `updated_at`

任意时刻 `running` 与 `cooldown` 租约总数不得超过 4。物理 GPU 编号和 UUID 组合唯一，一张卡不能拥有两个租约，一个任务也不能同时关联两个租约。

状态模式版本升级。旧运行目录保持原样，但不直接恢复到新租约状态机；新策略从新的运行目录开始。

## 首次获取 GPU

没有租约的 GPU 必须连续 5 次、每次间隔约 60 秒同时满足：

- 没有任何 compute PID；
- 显存占用不超过 512 MiB；
- GPU 利用率不超过 5%；
- GPU 编号与 UUID 映射稳定。

连续计数达到 5 后，启动前再进行两次相隔 3 秒的完整复查。两次都满足条件时才创建租约并启动下一条待处理任务。

候选 GPU 按物理编号升序处理。达到 4 个租约后，即使还有合格 GPU，也不再获取第五张卡。

## 运行期间出现其他进程

租约处于 `running` 时，如果后来出现其他用户 PID：

- 当前我方任务继续运行；
- 不停止我方或对方进程；
- 不释放正在运行的租约；
- 每分钟审计将该卡标记为 `SHARED`；
- 当前任务结束后进入正常 60 秒冷却，再决定是否继续使用该卡。

## 任务结束与 60 秒冷却

任务成功或非零退出后，关联租约进入 `cooldown`，并将 `cooldown_ready_at` 设置为结束时间后 60 秒。

到达冷却截止时间后，调度器检查：

- 没有任何 compute PID；
- 显存占用不超过 512 MiB；
- GPU 利用率不超过 5%；
- GPU UUID 未改变。

三项资源条件和 UUID 全部满足后，再执行两次相隔 3 秒的最终复查。复查通过时，租约直接复用给下一条待处理任务，不重新等待连续 5 分钟。

任一检查不满足时：

- 释放该租约；
- 记录明确的释放原因；
- 空出一个租约槽位；
- 该 GPU 若以后再次可用，必须重新连续空闲 5 分钟后才能重新获取；
- 调度器可以用同样的 5 分钟策略寻找其他 GPU 作为替代。

如果当前阶段暂时没有可派发任务，但仍有同阶段任务正在运行，冷却租约保持到阶段屏障解除。Phase B 开放后可直接按冷却复用规则领取 Phase B 任务。

## 任务顺序与阶段屏障

每次派发始终选择当前阶段序号最小的 `pending` 任务。多个冷却租约同时可用时，按 GPU 物理编号升序领取后续任务；处理完可复用租约后，再为剩余租约槽位获取新的 5 分钟候选卡。

Phase A 的任务全部进入终态后开放 Phase B。用于解除 Phase A 屏障的终态包括：

- `succeeded`
- `failed`
- `launch_failed`
- `interrupted`

Phase B 使用同一套租约池、任务顺序和失败处理规则。Phase C 不进入队列。

所有 Phase A 和 Phase B 任务进入终态后，队列完成。完成结果允许“部分成功”，并汇总每种终态的数量和任务编号。

## 失败与鲁棒性

### 训练任务非零退出

- 标记为 `failed`；
- 保存退出码、结束时间和日志路径；
- 不自动重试；
- 不设置全局暂停；
- 对应租约进入 60 秒冷却；
- 队列继续派发其他任务。

### 启动失败

- 标记为 `launch_failed`；
- 保存错误详情；
- 不自动重试；
- 释放对应租约；
- 该卡重新走 5 分钟审查；
- 其他租约和任务继续。

### 运行进程身份无法确认

- 标记为 `interrupted`；
- 不自动重试；
- 释放对应租约；
- 不直接复用原卡；
- 原卡只有重新通过连续 5 分钟审查后才可再次获取；
- 其他租约和任务继续。

### GPU 查询失败

单次 `nvidia-smi` 查询或解析失败时：

- 本轮不派发、不复用、不释放租约；
- 记录 `GPU_PROBE_ERROR`；
- 下一轮自动重新查询；
- 不永久暂停队列。

查询恢复后，调度器根据持久状态继续运行。连续失败只会使队列保持等待，不会在未知 GPU 状态下启动任务。

### 调度器完整性错误

以下错误采用失败关闭并让调度器非零退出：

- 状态文件无法原子写入；
- 状态模式、任务定义或命令摘要不匹配；
- 队列锁无法安全确认；
- GPU 编号与 UUID 映射发生无法解释的全局变化；
- 持久状态违反“最多 4 个唯一租约”等不变量。

这类错误不能通过跳过单个任务解决，继续派发可能导致重复训练或状态错乱。

## 状态恢复

恢复时验证：

- 命令摘要和任务定义；
- 状态模式版本；
- 租约数量不超过 4；
- GPU 与 UUID 唯一；
- `running` 租约与 `running` 任务一一对应；
- 运行任务的 PID、进程组、`/proc` 启动时间和命令摘要；
- `cooldown_ready_at` 可解析。

可验证的运行任务继续监控。可验证的冷却租约继续等待剩余冷却时间。无法确认的运行任务标记为 `interrupted`，其租约释放，其他任务继续。

## 日志

保留每分钟八卡 `GPU_AUDIT`，增加：

- `leases=3/4`（示例表示当前持有 3 个租约）
- `lease=NONE`
- `lease=RUNNING`
- `lease=COOLDOWN`
- `task=A05`
- `cooldown_ready_at=2026-07-30T12:01:00+0800`

增加租约事件：

- `GPU_LEASE_ACQUIRED`
- `GPU_LEASE_COOLDOWN`
- `GPU_LEASE_REUSED`
- `GPU_LEASE_RELEASED`

释放事件必须包含 `reason`，例如：

- `foreign_pid`
- `memory_above_limit`
- `utilization_above_limit`
- `uuid_changed`
- `launch_failed`
- `interrupted`
- `queue_complete`

任务事件继续记录 `TASK_START` 和 `TASK_END`。训练失败使用 `TASK_END result=FAILED`，启动失败使用 `TASK_END result=LAUNCH_FAILED`，身份中断使用 `TASK_END result=INTERRUPTED`。

队列结束记录：

```text
QUEUE_COMPLETE total=20 succeeded=17 failed=2 launch_failed=1 interrupted=0
```

日志字段不保存完整命令行、完整环境变量或潜在凭据。

## 测试策略

使用模拟时钟、GPU 快照、进程检查器和任务启动器，不启动真实训练，覆盖：

- 第 5 次连续空闲样本前不能获取租约；
- 最多只能创建 4 个租约，即使 8 张卡都空闲；
- 4 个租约包含 `running` 和 `cooldown`；
- 任务成功后进入 60 秒冷却；
- 冷却不足 60 秒不能启动下一任务；
- 冷却完成且三项条件满足时复用同一 GPU；
- 冷却完成但出现其他 PID时释放租约；
- 冷却完成但显存或利用率超限时释放租约；
- 释放后必须重新累计 5 个空闲样本；
- 释放一个租约后可以获取另一张合格 GPU，但总数仍不超过 4；
- 运行期间出现其他 PID 时当前任务不停止；
- 训练非零退出后其他任务继续；
- 启动失败或身份中断后其他租约继续；
- Phase A 含失败时，全部达到终态后仍进入 Phase B；
- 单次 GPU 查询失败只跳过本轮，下一轮恢复；
- 状态恢复验证 4 卡上限、唯一性和冷却截止时间；
- 部分成功队列输出正确汇总；
- 完整测试套件通过。

## 验收标准

- 调度器从不同时持有超过 4 张 GPU。
- 首次获取任何 GPU 必须通过连续 5 分钟审查和最终复查。
- 已租用卡的任务结束后至少间隔 60 秒才可继续下一任务。
- 原卡只有在无 compute PID、显存不超过 512 MiB、利用率不超过 5%且 UUID 稳定时才能快速复用。
- 原卡不满足条件时立即释放，并重新走 5 分钟策略。
- 单个任务失败不会阻塞其他任务，也不会阻止 Phase B。
- GPU 查询短暂失败不会永久暂停队列。
- 调度器完整性错误仍失败关闭。
- 日志和状态能解释每个任务、租约及最终失败汇总。
- 实现完成后不自动启动 GPU 队列。
