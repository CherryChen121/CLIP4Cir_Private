# Combined 安全多卡队列设计

## 目标

在没有 Slurm 等系统级调度器的共享服务器上，定期检查 GPU 0–7，只在显卡经过连续空闲审查后，按 `命令.sh` 中的顺序派发 Combined Phase A 和 Phase B 训练任务。系统以不干扰其他用户为最高优先级，并在任何不确定状态下停止派发。

## 已确认的运行策略

- 使用多卡队列：多张显卡通过审查时，可以同时运行多个任务。
- Phase A 的 10 个任务按原顺序派发。
- Phase A 全部成功后，才允许派发 Phase B 的 10 个任务。
- Phase C 不加入本队列。
- 任一任务非零退出后，停止派发新任务；已经运行的任务继续完成。
- 调度器实现与验证期间不启动训练。真实派发必须显式使用 `--run`。

## 方案选择

### 不采用：只轮询 `gpustat`

瞬时利用率为 0 不代表显卡无人使用。本机当前 GPU 0、1、4、5 就存在利用率为 0、但有计算进程并占用约 15–17 GiB 的情况。

### 采用：保守型用户态调度器

使用 `nvidia-smi` 同时检查计算进程、显存和利用率，经过连续观察与派发前复查后才启动任务。该方案不需要管理员权限，可以在当前环境实施。

### 当前不可用：Slurm 或 GPU 独占模式

本机没有 `sbatch`、`srun`、`squeue` 或 `scontrol`。修改 NVIDIA 独占模式需要管理员权限，并可能影响现有任务，因此本功能不执行任何此类系统配置。

## 组件

### 1. 命令读取器

从 `命令.sh` 的 `COMBINED_COMMANDS_BEGIN/END` 区域读取命令，仅选择 Phase A 和 Phase B。

- 必须恰好读取 Phase A 10 条、Phase B 10 条。
- 必须保留文件中的任务顺序。
- 只接受当前固定格式：环境变量、`nohup python src/<entry>.py`、参数、日志重定向及后台符号。
- 使用 `shlex` 解析并转换为参数数组，不使用 `eval`。
- 运行时把固定的 `CUDA_VISIBLE_DEVICES=0` 替换为被选中的物理 GPU 编号。
- 每个进程只看到一张卡，因此训练代码不会跨卡执行 DataParallel。

### 2. GPU 审查器

每 60 秒通过 `nvidia-smi` 查询 GPU 指标和计算进程。单张 GPU 必须连续 5 次同时满足以下条件，才成为候选：

- 没有任何 compute PID；
- 显存占用不超过 512 MiB；
- GPU 利用率不超过 5%；
- `nvidia-smi` 查询完整成功，GPU UUID 与编号映射稳定。

任意指标缺失、无法解析、查询失败或发现 PID 时，均按“占用”处理，并把该 GPU 的连续空闲计数清零。即使进程利用率为 0，也只要 compute PID 存在就绝不使用。

### 3. 派发前竞态防护

候选 GPU 在启动任务前进行两次完整复查，两次间隔 3 秒。任一次不满足条件就取消本次派发。

调度器使用 `flock` 保证同一项目同时只有一个派发实例。该锁只能协调本项目，不能阻止其他用户在复查后启动任务，因此不能提供系统级绝对独占保证。

### 4. 任务运行与冲突保护

每张 GPU 同时最多运行一个本队列任务。任务以独立进程组启动，调度器只保存和管理自己创建的 PID、进程组及 `/proc` 启动标识。

每个任务由一个最小 Python 监督进程启动。监督进程从调度器原子写入的任务清单读取参数数组，以 `shell=False` 启动训练、等待退出，并把退出码原子写入任务结果文件。这样调度器自身重启后仍能确认训练结果；监督进程不解析 shell 文本、不查询或管理其他用户进程。

任务清单不保存完整进程环境，只保存白名单化的 `CUDA_VISIBLE_DEVICES` 与 `NCCL_P2P_DISABLE` 覆盖值，避免把令牌、密钥或其他环境凭据写入状态目录。

调度器每 30 秒检查运行状态和 GPU compute PID：

- 如果只存在本任务进程树中的 PID，继续运行。
- 如果发现任何未知 PID，立即暂停整个队列的新派发。
- 为保护后来进入显卡的其他用户任务，向我们自己的进程组发送 `SIGTERM`。
- 等待最多 30 秒；如自己的进程仍未退出，只对自己的进程组发送 `SIGKILL`。
- 绝不向未知 PID 或其他用户进程发送信号。
- 将任务标记为 `conflict_stopped`，记录未知 PID、用户名、GPU 和时间，等待人工处理。

这一策略只能缩短无调度器环境中的竞态重叠时间，无法从操作系统层面完全阻止其他用户与本任务在同一秒选择同一张卡。

### 5. 队列状态机

任务状态为：

- `pending`
- `running`
- `succeeded`
- `failed`
- `conflict_stopped`
- `interrupted`

Phase A 内按顺序选择 `pending` 任务，多张合格 GPU 可以连续领取后续任务。只有 10 个 Phase A 任务全部为 `succeeded`，Phase B 才能开始。

出现 `failed`、`conflict_stopped` 或无法确认身份的 `interrupted` 状态时：

- 不再启动新任务；
- 已运行任务继续完成，冲突任务除外；
- 不自动重试或跳过；
- 不进入下一阶段。

### 6. 持久化与恢复

每次运行在被 Git 忽略的 `gpu_queue_runs/<run-id>/` 下创建：

- `state.json`：队列、状态、PID、进程启动标识、GPU、时间和退出码；
- `dispatcher.log`：GPU 审查、派发、暂停与恢复事件；
- `logs/`：每个训练任务的标准输出和标准错误。

状态文件通过“写临时文件再原子替换”更新。恢复时同时核对 PID、`/proc` 启动时间和命令摘要，防止 PID 重用导致误认。无法确认的旧 `running` 任务标记为 `interrupted` 并暂停，而不是自动重跑。

每个运行目录保存 `命令.sh` Combined Phase A/B 内容的 SHA-256。命令发生变化时拒绝直接恢复旧队列。

### 7. 启动接口

提供三个明确入口：

- `--dry-run`：解析并审查 20 条命令，显示当前 GPU 状态和预计行为，不启动任务。
- `--run`：创建新运行目录并开始真实轮询和派发。
- `--resume <run-dir>`：恢复指定运行目录；恢复前必须通过命令摘要、PID、`/proc` 启动时间和命令身份校验，任何不确定状态都会暂停而不是启动新任务。

真实调度器通过 `nohup` 后台运行。重复启动会被 `flock` 拒绝，并给出当前调度器 PID/状态位置。停止调度器只停止后续派发；是否终止本项目已运行任务必须使用单独、显式的操作，不作为普通停止行为。

## 启动前预检

`--dry-run` 和 `--run` 都必须先完成以下检查：

- Combined 标记唯一且 Phase A/B 各 10 条；
- 不包含 Phase C；
- 20 个日志名唯一；
- Python 环境、训练入口、数据集根目录存在；
- 所有命令中的显式模型路径存在；
- 参数能被对应入口接受；
- `nvidia-smi` 和 `flock` 可用；
- 状态与日志目录可写；
- 当前没有第二个调度器实例。

任何预检失败都禁止派发。

## 测试策略

自动化测试不启动真实训练，使用模拟的 `nvidia-smi` 输出和短生命周期子进程覆盖：

- 有 compute PID 时，即使利用率为 0 也不判空闲；
- 显存或利用率超过阈值时不判空闲；
- 连续 5 次合格后才成为候选；
- 派发前任一次复查失败时不启动；
- 多卡按 GPU 编号和任务顺序分配；
- Phase A 未全部成功时不进入 Phase B；
- 失败后暂停新派发；
- 未知 PID 只导致终止自己的进程组；
- 状态原子写入、恢复校验与命令摘要变更拒绝；
- 双实例锁拒绝；
- dry-run 永远不创建训练子进程。

实施完成后还要执行一次真实只读预检，确认当前八张被占用的卡全部被正确报告为不可用。

## 安全边界

- 不执行 `kill`、`SIGTERM` 或 `SIGKILL` 于任何非本调度器创建的进程。
- 不修改 NVIDIA compute mode、MIG、MPS、驱动或系统服务。
- 不使用当前存在 compute PID 的 GPU。
- 不覆盖已有训练日志。
- 不把完整环境变量或潜在凭据写入任务清单、状态或日志。
- 不自动启动 Phase C。
- 不在实施或测试阶段启动训练。
- 没有系统级调度器时无法承诺零竞态；检测到竞态后的唯一自动动作是停止自己的任务并暂停队列。
